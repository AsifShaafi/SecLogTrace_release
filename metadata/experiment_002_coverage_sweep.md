# experiment_002 — Coverage Sweep (Labmate UI Session)

> **Status: DEV / COVERAGE DATA, NOT CORPUS DATA.** A hand-clicked UI
> session cannot be regenerated — two people following the same protocol
> produce different timing, ordering, and trace counts. This experiment's
> purpose is to discover the `root_operation` inventory and endpoint
> surface so `generate_baseline_traffic.py` can be extended to cover it.
> The corpus itself must be generated by that script, reproducibly, not by
> this session. Do not cite any count from this experiment in a paper.

### Failures observed (per the labmate's log)
- Entries 6, 8, 9: "no response from the website" on three consecutive
  trip searches (Shanghai↔Suzhou, 8/18 departure date). Entry 7 was a
  re-login performed in response to entry 6's failure — a single retry,
  not a repeated pattern.
- Entry 32: could not find a UI path to request a voucher/receipt.
- **HAR correction to the session log:** all three "no response" searches
  (entries 6, 8, 9) show as `POST travelservice/trips/left` /
  `travel2service/trips/left` returning **HTTP 200** in the HAR. The
  backend answered; the browser did not render in time. These are valid,
  successful search traces despite being logged as failures by the
  operator. **Where the session log and the HAR disagree, the HAR is
  authoritative for data purposes** — it reflects what the system did, the
  session log reflects what the operator perceived.
- Four genuine API-level failures found only in the HAR (not visible to
  the operator, since the admin pages still rendered): `GET
  admintravelservice/admintravel` (×2) and `GET adminorderservice/adminorder`
  (×2) returned **HTTP 403**. Cause not yet investigated — possibly a
  missing/expired admin auth header on those two specific admin endpoints.
  Flagged for follow-up; not blocking, since 403 is itself a valid traced
  outcome for now.
- Entries 45–47 (fullscreen button, logo click, avatar click): logged as
  "doesn't do anything." Corroborated independently by the raw log
  collection — `ts-avatar-service`, `ts-news-service`,
  `ts-ticket-office-service`, and `ts-voucher-service` all produced **0**
  log lines and do not appear among the 42 services Jaeger exported.
  Consistent explanation: these UI elements are not wired to a backend
  call on this deployment (or the services aren't deployed at all — needs
  confirming against the live pod list before treating this as a frontend
  finding rather than a missing-service finding).
- Entry 39: no second travel list exists in the admin UI on this
  deployment (the two-backend G/D vs Z/K/T split visible elsewhere did not
  surface a second admin list view).

### Parsing — bugs found in `build_feature_table.py`, fixed, re-verified

Ran `parse_jaeger_traces.py --input-dir ... --output-dir
data/processed/traces/experiment_002 --label normal`. Output:
`spans.csv` (37,092 rows), `traces.csv` (5,031 rows — **not
deduplicated**, contains one row per service occurrence per trace; see
below).

First run of `build_feature_table.py` against this output produced
**439 retained rows**, not the expected 123. Root cause: two bugs in the
script, both now fixed and re-verified against this data.

**Bug 1 — fan-out on merge.** `build_feature_table.py` merges
`traces.csv`'s label/noise columns onto the per-trace feature table with a
plain `merge(..., on="trace_id")`. Because `traces.csv` has multiple rows
per `trace_id` (one per originating service export, per the dedup note
above), the merge is one-to-many and duplicates every feature row once per
match. 439 = exactly the 123 real traces, each repeated by its individual
fan-out count (verified: `4*1 + 71*2 + 20*3 + 6*4 + 1*5 + 10*6 + 5*10 +
1*11 + 1*12 + 2*17 + 1*18 + 1*19 = 439`, matching the "real traces only"
fan-out table from `corpus_audit.py` exactly). Fix: deduplicate
`traces.csv`'s trace-level columns on `trace_id` before merging, since
label/noise/experiment_id are trace-level attributes identical regardless
of which service emitted the row. An assertion now guards against
recurrence.

**Bug 2 — root_operation ignored `http.target`.** Independent of bug 1,
`build_feature_table.py` has always stratified on the raw span
`operationName` only, never the `http.target`/`http.url` tag — even though
the equivalent fix was made and verified in `corpus_audit.py` several
sessions earlier. The two scripts had diverged. Fixed by porting the same
normalization (prefer the URL tag, fall back to operation name, collapse
numeric path segments to `{id}`).

## Anomaly flagged for later investigation
`GET admintravelservice/admintravel` root operation shows **median 259
spans** across 6 real traces — by far the largest in the per-endpoint
table (next highest is ~30). This is also the endpoint that returned 403
twice in the HAR. Possible connection between the failed-auth path and
abnormal span count not yet checked. Not blocking; noted so it isn't lost
before Phase 2 corpus design.

## Notes for Phase 1/2
- This session is the first evidence of real coverage beyond the 4
  booking-flow services. The `root_operation` inventory it produced is the
  actual deliverable — it becomes the worklist for extending
  `generate_baseline_traffic.py`.
- Four services with zero traffic in this session
  (avatar/news/ticket-office/voucher) need a pod-list check
  (`kubectl get pods | grep -E 'avatar|news|ticket-office|voucher'`) before
  concluding they're simply unused UI vs. not deployed at all.
- The traces.csv dedup discrepancy above should be treated as a standing
  reminder: **any script that reads Jaeger exports must dedup on
  `(trace_id, span_id)` before reporting a count.** `parse_jaeger_traces.py`
  currently does not; `build_feature_table.py` and `corpus_audit.py` do.
  Worth a fix to `parse_jaeger_traces.py` itself so its console output
  stops being misleading, even if downstream tools already compensate.
