# SUT2 (TeaStore) Setup — Stages 1–2 (2026-09-11)

Getting TeaStore instrumented with OpenTelemetry so it produces the same
trace+log corpus as SUT1 (Train-Ticket). Companion to
`docs/SUT2_SELECTION_20260910.md` (why TeaStore) and the second-SUT handoff.
Windows/PowerShell commands (native x86 — no ARM emulation).

## Status
- **Stage 1 — TeaStore runs: DONE.** `docker-compose_default.yaml` brings up
  all 6 services with the DB connected; WebUI returns HTTP 200 at
  `http://localhost:8080/tools.descartes.teastore.webui/`.
- **Stage 2 — add OTel: this doc.** `docker-compose_otel.yaml` adds a Jaeger
  backend and attaches the OTel Java agent to the 5 Java services.

## Verified facts this build rests on (2026-09-11)
- `JAVA_TOOL_OPTIONS` IS honored by the TeaStore images (probe:
  `-Dseclogtrace.probe=true` was picked up and echoed by the JVM). So OTel
  attaches by env var — **no image rebuild needed.**
- TeaStore login failure signal: **both good and bad logins return HTTP 302**
  (status won't separate them, like SUT1). They differ in the redirect
  `Location` (`.../webui/` on success vs `.../webui/login` on failure) and the
  response cookie (`teastoreMessageCookie=You_are_logged_in!` vs
  `teastoreErrorMessageCookie=You_used_wrong_credentials!`). **Record this: the
  credential-abuse signal on SUT2 lives in redirect-target/cookie, a different
  locus than SUT1 — a cross-system RQ3 finding.**
- Services: `registry, db, persistence, auth, image, recommender, webui`.
  Java services (get OTel): all except `db` (MySQL) and `registry`... actually
  `registry` IS Java but is infra; it's left instrumented-optional (add the
  same env block if you want registry spans, usually not needed for the corpus).

## Step 1 — place the OTel compose file
Copy `docker-compose_otel.yaml` into `TeaStore/examples/docker/` alongside the
default one. Stop the plain stack first so ports don't clash:

```powershell
cd <teastore-checkout>
docker compose -f docker-compose_default.yaml down
```

## Step 2 — bring up the instrumented stack
```powershell
docker compose -f docker-compose_otel.yaml up -d
```

`otel-init` downloads the agent jar into a shared volume first; the Java
services wait on it (`depends_on`). First boot is slower (agent download + all
WARs). Watch progress:

```powershell
docker compose -f docker-compose_otel.yaml ps
docker compose -f docker-compose_otel.yaml logs -f webui
```

Wait for the webui WAR to finish deploying (~45s once it starts), then confirm
the app still serves:

```powershell
curl.exe -I http://localhost:8080/tools.descartes.teastore.webui/
```

## Step 3 — confirm the OTel agent attached
Look for the agent's own startup line in a service's logs:

```powershell
docker compose -f docker-compose_otel.yaml logs webui | Select-String "opentelemetry|OpenTelemetry|javaagent"
```

You want a line like `[otel.javaagent] ... OpenTelemetry Javaagent started`.
If instead you see a Java-8 incompatibility error, edit `otel-init`'s URL in
the compose to the 1.32.1 agent (noted in the file) and
`docker compose -f docker-compose_otel.yaml up -d --force-recreate`.

## Step 4 — THE VERIFICATION GATE (the make-or-break)
Drive one real request through the app, then confirm a cross-service trace
lands in Jaeger. A login is ideal because it crosses webui -> auth
-> persistence -> db:

```powershell
curl.exe -i -c cookies.txt -X POST `
  "http://localhost:8080/tools.descartes.teastore.webui/loginAction" `
  -d "username=user1&password=password&signin=Sign+in"
```

Note: `user1`/`password` is TeaStore's built-in public demo fixture (the
default seeded login), not a real credential.

Then open Jaeger: **http://localhost:16686**
- Service dropdown should list `webui`, `auth`, `persistence`, etc.
- Find the login trace. It should span MULTIPLE services (webui -> auth ->
  persistence -> a JDBC span to db), not a single service.

**This is the gate.** If you see a multi-service trace, SUT2 tracing works and
the entire SUT1 pipeline transfers. If you see only single-service traces (or
only `webui`), context isn't propagating across TeaStore's Ribbon/registry
calls — stop and debug that before anything else (see Troubleshooting).

## Step 5 — trace_id in logs (the join key)
The corpus joins logs to traces by `trace_id`. Confirm the agent is injecting
trace context into the app logs, or configure it:

```powershell
docker compose -f docker-compose_otel.yaml logs auth | Select-String "trace_id|traceId"
```

If trace_id is absent from log lines, set (on each Java service) the OTel log
auto-injection or a logging pattern that includes MDC `trace_id`, mirroring
SUT1's `enable_trace_id_logging.sh` approach. TeaStore uses Tomcat/JULI +
SLF4J; the exact pattern edit is a Stage-2b task — get the trace side working
(Step 4) first.

## Troubleshooting
- **Only single-service traces / no cross-service spans.** TeaStore uses a
  client-side (Ribbon) load balancer over the registry. The OTel agent
  instruments the HTTP client it uses (Apache HttpClient / HttpURLConnection),
  so W3C trace context SHOULD propagate. If it doesn't, check the agent
  version instruments TeaStore's specific client, and that
  `OTEL_PROPAGATORS=tracecontext` is set (it is, in the compose).
- **Agent fails to attach on Java 8.** Switch `otel-init` to the 1.32.1 agent
  URL (in the compose comments) — 1.x explicitly supports Java 8.
- **Kieker conflict.** The images run Kieker's `-javaagent` too; two agents
  can coexist. If startup fails with an agent/AspectJ error, the OTel agent
  should load first (JAVA_TOOL_OPTIONS is prepended) — if there's a genuine
  clash, disabling Kieker (it already reports Status: 'disabled') by clearing
  its config is the fallback.
- **Port clash on 8080/3306.** Ensure the default stack is `down` before `up`.

## After the gate passes — what changes for the pipeline
Once cross-service traces + trace_id-in-logs both work, the SUT1 scripts
transfer with SUT2 endpoint strings:
- `export_jaeger_traces.sh` — points at this Jaeger (localhost:16686 API);
  same dedup/manifest logic.
- `generate_abuse_traffic.py` / `generate_ssrf_traffic.py` — swap Train-Ticket
  endpoints for TeaStore's (login = `/loginAction`; catalog/search endpoints
  for resource-exhaustion + injection; the `image` service as the SSRF
  injection host — the avatar-service analogue).
- `corpus_audit.py`, `build_feature_table.py`, `stratification.py`,
  `run_detection.py` — unchanged (same feature schema, the whole point).

|---|---|---|
| Credential abuse | `/users/login` | `/loginAction` (signal in redirect/cookie, not status) |
| Resource exhaustion | trip search | a catalog/category/product-list endpoint (find the expensive one) |
| Injection | trip search station field | a search/query param that reaches the DB |
| Data exfiltration | admin bulk reads | catalog bulk reads / any admin-ish list; TeaStore's admin surface is thinner — confirm what bulk-read exists |
| SSRF (injected) | avatar service `src_url` | `image` service — confirm it fetches by URL / can host an injected sink |

The exfiltration and SSRF mappings are the two that need the most checking on
SUT2 — TeaStore's admin/bulk surface is thinner than Train-Ticket's, and the
image service's code needs inspection to confirm it's an SSRF-injection
candidate like avatar was. Flag early if either doesn't fit; they may need a
small injected endpoint (documented as such, like SUT1's SSRF).
